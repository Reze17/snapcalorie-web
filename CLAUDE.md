# SnapCalorie Web

An AI meal-photo calorie tracker. Built in 10 sequential phases (see README "Phase status"); one phase per Claude Code session, each gated by its own verification checklist before the next starts.

## Non-negotiable rules

These are correctness/UX requirements from the FRD that are easy to violate accidentally. They apply across every phase, not just the phase that first introduces the feature.

- **Timezone-correct days.** `meal_entries.logged_at` is `TIMESTAMPTZ`, but `daily_summaries.summary_date` is a `DATE` in the user's timezone (`users.timezone`). Never derive "which day" from server local time or UTC.
- **Historical targets are immutable.** `daily_summaries.target_calories` is a snapshot written when a day's first entry lands. Changing `users.daily_calorie_target` must never rewrite past summaries.
- **Upsert summaries.** `daily_summaries` has `UNIQUE(user_id, summary_date)` — always `INSERT ... ON CONFLICT DO UPDATE`, never a blind insert.
- **Money-style numerics.** Calories/macros are `NUMERIC`, not floats. Use a decimal type end-to-end; no float math on macros.
- **Confidence range.** `meal_items.ai_confidence` is stored 0.00–1.00; the ambiguity threshold is `< 0.70`.
- **Linear portion scaling.** `value_new = value_0 × (m_new / m_0)`. Any manual edit to a portion/value sets `is_user_edited = TRUE`.
- **Non-punitive UI.** Over-target states never use blocking modals, red alarm styling, or guilt language — neutral, factual, informational only.
- **Responsive 360px → 4K.** Mobile-first; nothing may horizontally scroll at 360px.

## Stack

Next.js 15 (App Router) + TypeScript (strict) · PostgreSQL + Drizzle ORM · Tailwind (mobile-first, `xs` breakpoint at 360px) · Vitest · S3-compatible storage (later phases).

## Commands

- `npm run dev` — start the dev server
- `docker compose up -d` — start local Postgres + MinIO (if using Colima instead of Docker Desktop, run `colima start` first, and prefix docker/compose commands with `DOCKER_CONTEXT=colima` if multiple Colima profiles exist)
- `npm run db:generate` / `npm run db:migrate` / `npm run db:studio` / `npm run db:seed` — Drizzle migrations + demo data
- `npm run test` — Vitest
- `npm run e2e` — Playwright (starts/reuses the dev server itself; needs Postgres + MinIO up first)
- `npm run lint` / `npm run typecheck` / `npm run format:check`

**Never run `npm run build` while a `next dev` process is also running against the same working copy** — both write to `.next/`, and a concurrent production build corrupts the dev server's routing state (every route starts 404ing until it's restarted). Stop the dev server first, build, then restart it if you still need it.

## Data access layer (Phase 1)

- `src/db/schema.ts` — Drizzle schema for `users`, `meal_entries`, `meal_items`, `daily_summaries`.
- `src/server/repositories/` — typed repository functions. `createMealEntryWithItems`, `updateMealEntry`, and `deleteMealEntry` each run in a single transaction and always call `recalculateDailySummary` for every affected local day afterward.
- `src/server/lib/timezone.ts` — the only place day-boundary math should happen (`localDayRangeUtc`, `instantToLocalDate`), per the timezone-correctness rule above.
- Macro/calorie arithmetic uses `decimal.js`; all `NUMERIC` columns round-trip as strings, not JS numbers.

## Auth (Phase 2)

- `src/auth.ts` — Auth.js (NextAuth v5) config: Credentials (email/password, bcryptjs) + Google, `@auth/drizzle-adapter` against `users`/`accounts`/`sessions`/`verification_tokens`.
- **Session strategy is `"jwt"`, not `"database"`, on purpose.** Auth.js's Credentials provider always issues a JWT-encoded cookie and never creates an adapter session row, regardless of the configured strategy (see `node_modules/@auth/core/lib/actions/callback/index.js`) — so "database sessions" isn't actually available for email/password. Using `jwt` globally keeps Google on the same cookie format and keeps `src/middleware.ts` Edge-compatible.
- `users` table: the Drizzle **JS property is `id`** (required by `@auth/drizzle-adapter`'s expected shape) but the **DB column stays `user_id`** — don't rename the column, and don't reintroduce a separate `userId` property on that table.
- `Google({ allowDangerousEmailAccountLinking: true })` is required for FR-01's "same email reuses the same user" behavior — this is Auth.js's own documented opt-in, not an oversight.
- `src/middleware.ts` uses `next-auth/jwt`'s `getToken()` directly instead of importing `@/auth` — importing the full config would pull `pg` and `bcryptjs` into the Edge middleware bundle and break it. Extend `PROTECTED_PREFIXES` there (and rely on the `(app)` layout's server-side `auth()` check as a backstop) as new protected routes are added in later phases.
- Google OAuth needs real `AUTH_GOOGLE_ID`/`AUTH_GOOGLE_SECRET` credentials to test; email/password needs no external setup. See README "Testing auth end to end".
- **`DEV_BYPASS_AUTH=true`** (set in a local `.env` only, never committed as `true`, never read in CI) skips the login redirect everywhere and auto-provisions a fixed `dev-bypass@snapcalorie.local` user — added for fast manual testing of protected routes without signing in. `src/server/dev-bypass.ts`'s `getEffectiveUser()` is what every protected page/action calls instead of raw `auth()`; a real session still always wins over the bypass user if one exists. Turn it off (`false` or delete the line) to test real login again — nothing else needs to change. **Every new protected page/Server Action must call `getEffectiveUser()`, never `auth()` directly** — `/analyze`'s page.tsx was missed when this was introduced and silently redirected to `/login` even with the bypass on (auth() alone correctly returns null with no real session; only `getEffectiveUser()` knows about the bypass fallback). Grep for `await auth()` outside `src/auth.ts`/`dev-bypass.ts` itself when adding a new route to catch this.

## Vision service (Phase 3)

- `src/server/vision/types.ts` is the provider-agnostic contract (`INutritionVisionService`, `AnalysisResult`, `DetectedFood`, `FoodSearchResult`). Nothing provider-specific may leak into it — no vendor SDK types, ever.
- **Every `DetectedFood` carries `per100g`.** Phase 6's portion-edit rescaling (`value_new = value_0 × (m_new / m_0)`, see rule above) needs that fixed baseline — don't drop it when a later phase touches this code.
- `src/server/vision/factory.ts`'s `getVisionService()` is the only place `VISION_PROVIDER` is read. Call sites depend on the interface only, never on `MockVisionService` (or any future provider class) directly.
- `src/server/vision/normalize.ts` maps `AnalysisResult` → `meal_items` row shape (fixed-point strings at the column scale, confidence clamped to `[0,1]`) — this is what Phase 5/6 should call before inserting, not ad-hoc rounding.
- `src/server/vision/contract.ts`'s `runVisionServiceContractTests(label, factory)` must be run against any new provider implementation (openai/anthropic/google, when they land) in addition to that provider's own tests.
- `MockVisionService` scenarios (`default | lowConfidence | singleItem | empty | timeout`) are the fixtures later phases should build their UI/tests against — see README "Vision service (mock)".

## Capture, upload & storage (Phase 4)

- `src/lib/image/process.ts` (`processImageFile`) validates (type + 20MB cap), downsamples to `MAX_EDGE_PX` (1920), and re-encodes to JPEG at `JPEG_QUALITY` (0.85) — client-side only, runs in the browser.
- **Do not add manual EXIF-orientation correction back into this pipeline.** It used to exist (`getOrientedCanvasSize`/`applyOrientationTransform`, removed in Phase 4) and was verified — by hand-crafting a real EXIF-tagged JPEG and inspecting it in a real browser — to double-rotate portrait photos: `createImageBitmap` (with or without `imageOrientation: "none"`) and `<img>`/`naturalWidth`/`naturalHeight` all already return EXIF-corrected dimensions/pixels in current evergreen browsers, with no reliable way to opt out. `computeDownsampleDimensions` (`src/lib/image/resize.ts`) is the only "resize helper"; it just works off whatever width/height the browser reports, which is already orientation-correct.
- `src/server/storage/` is the S3-compatible storage layer (`@aws-sdk/client-s3` + `s3-request-presigner`), MinIO locally (`docker-compose.yml`'s `minio`/`minio-init` services) via `S3_ENDPOINT` + `forcePathStyle`. `createPresignedUploadUrl(userId)` always derives the key from the **authenticated session's** user id (`users/{userId}/meals/{uuid}.jpg`) — never accept a client-supplied userId for this. Both upload and download presigned URLs expire in exactly `PRESIGNED_URL_EXPIRY_SECONDS` (15 min); the bucket itself is never made public.
- `/capture` → upload → `/analyze?key=...` is the flow; both routes (plus `/dashboard`, `/profile`) are in `PROTECTED_PREFIXES` in `src/middleware.ts`.
- `e2e/` holds the Playwright suite (`npm run e2e`) — real browser, real MinIO, no mocking. `e2e/fixtures/sample-meal.jpg` is a small checked-in JPEG; don't commit large fixtures.

## Real vision provider (Phase 5)

- `src/server/vision/anthropic-vision-service.ts` implements `INutritionVisionService` against Claude's Messages API (multimodal), selected via `VISION_PROVIDER=anthropic` + `VISION_API_KEY` (falls back to `ANTHROPIC_API_KEY`). The interface itself was **not** modified — do not add Anthropic-specific fields to `types.ts`.
- **The model is never trusted to do the arithmetic.** It's asked for `portionGrams`, `confidence`, and `per100g` macros only (see `src/server/vision/schema.ts`'s `rawDetectedFoodSchema` — no top-level absolute macros); `toDetectedFood()` in `anthropic-vision-service.ts` derives the absolute `calories`/`protein`/`carbs`/`fat` deterministically as `per100g × (portionGrams / 100)`. This guarantees the per100g/absolute pair stays internally consistent for Phase 6's rescaling, and eliminates a whole class of LLM-arithmetic errors. Don't ask the model for absolute macros directly.
- Structured output uses forced tool-use (`tool_choice: { type: "tool", name: ... }`, `strict: true`) rather than "please output JSON" prompting — far more reliable. Every tool call is still validated with zod (`rawAnalysisSchema` / `foodSearchListSchema`) before being trusted.
- **Two independent retry mechanisms, don't conflate them:** (1) network-level timeout/retry (12s timeout, 1 retry with backoff) is handled entirely by the Anthropic SDK client's `timeout`/`maxRetries` options — no hand-rolled backoff code exists or should exist; `APIConnectionTimeoutError` is caught and rethrown as `VisionServiceTimeoutError`. (2) schema-validation retry (model responded, but the JSON didn't match) is hand-rolled in `callForToolInput()`: exactly one repair attempt via a `tool_result` with `is_error: true` describing the zod error, then `VisionAnalysisFailedError` if it still doesn't validate.
- `VisionAnalysisFailedError` / `VisionServiceTimeoutError` are caught in `src/app/(app)/analyze/actions.ts`'s `runAnalysis()` and turned into a `{ status: "failed", message }` outcome — the UI (`AnalysisView.tsx`) shows a retry button and the manual-search/custom-entry fallback; it never throws to an error boundary or loses the uploaded photo/key.
- `/analyze?key=...` is user-tampered-with-able. `runAnalysis`/`assertOwnedKey` in `actions.ts` verifies the key is prefixed `users/{effectiveUserId}/meals/` before touching storage — never fetch an object for a key that doesn't match the caller's own effective user (see dev-bypass note above).
- `runVisionServiceContractTests` runs against `AnthropicVisionService` too (with the Anthropic SDK client mocked, no real network) in `anthropic-vision-service.test.ts` — keep doing this for any future real provider.
- Structured JSON logging (`console.info` with `event: "vision_analysis"`, `processingMs`, etc.) exists for Phase 10 to check the 4s end-to-end latency budget against — don't replace it with unstructured logging.

## Review & edit screen (Phase 6)

- `src/lib/portion-scaling.ts` is the ONE implementation of the linear scaling rule (`scaleValue`, guarded against `m_0 = 0`) and `computeAbsoluteMacros(per100g, grams)`. Every place that recomputes macros — portion-grams edit, swap-to-alternative, replace-via-search, custom entry's derived per100g — goes through this, always scaling from the food's fixed `per100g` baseline rather than the previously-displayed value, so repeated edits never compound rounding. Client-side (runs in the browser, no round-trip) — don't move it under `src/server/`.
- `AnalysisView.tsx`'s `EditableItem` (`{ localId, item: DetectedFood, isUserEdited }`) is a client-only wrapper — `isUserEdited` is not part of `DetectedFood`/`types.ts` and must stay that way (provider-agnostic contract). Grams edits, swaps (alternative chip or "Replace via search"), and any add (search result or custom entry) all set `isUserEdited = true`; only a portion-grams edit leaves `confidence`/`alternatives` untouched — swapping always resets `confidence: 1, alternatives: []` since the user just confirmed a specific identification.
- `saveMealAction` (`analyze/actions.ts`) computes entry-level totals as the Decimal sum of the _unrounded_ item values, rounds once, then calls `normalizeDetectedFood(item, isUserEdited)` per item (its second param exists for exactly this — don't revert to always passing `false`) before handing everything to `createMealEntryWithItems` (Phase 1), which does the insert-entry+items transaction and `recalculateDailySummary` call. Saving does not re-derive totals from rounded per-item values — that would violate "totals always equal the exact sum of items."
- `data-testid="item-card"` + `data-food-name="..."` on each item card exist solely for Playwright targeting (`e2e/review-and-save.spec.ts`) — keep them if you touch this component's markup.
- The sticky bottom totals/save bar is deliberately inset (not full-bleed edge-to-edge) to avoid negative-margin layout fragility inside the `(app)` layout's padded container — that's a considered simplification, not an oversight.

## Dashboard & entry detail (Phase 7)

- `src/lib/daily-metrics.ts`'s `computeDailyMetrics(consumed, target)` is the ONE place the FRD §4 totals formulas live (`remaining = target - consumed`, `achievementPercentage = consumed/target*100`, both via Decimal). It deliberately does **not** clamp or branch on over/under-target — that split is a rendering choice in `dashboard/page.tsx`, not a math one. Don't add an `isOverTarget` flag or similar to this function.
- **Non-punitive rendering (FR-08) lives entirely in how `dashboard/page.tsx` reads `metrics`, not in a separate "safe mode".** The progress bar fill color, the "N kcal remaining" / "N kcal over target" copy, and the percentage text all use the exact same classes regardless of whether `remaining` is positive or negative — there is no conditional styling branch for "over target" anywhere, which is what makes it structurally impossible to accidentally reintroduce red/alarm styling. Keep it that way: if a future change needs an `if (metrics.remaining < 0)` branch that changes a _color_ (not just wording), that's the FR-08 regression to catch in review.
- **No meal-type grouping, ever.** The dashboard timeline and `getEntriesWithItemsForUserDay` order strictly by `logged_at`; there is no "Breakfast/Lunch/Dinner" concept anywhere in the schema, repositories, or UI. Don't add one, even as a display-only label.
- `meal_items` has no `per100g` column (matches the FRD DDL exactly, unchanged since Phase 1). The entry-detail edit view (`entries/[entryId]/page.tsx`'s `toDetectedFood()`) reconstructs it on the fly as `storedValue / (storedGrams/100)` — exact modulo the 2-decimal rounding already baked into the stored row. This is why editing a _saved_ entry can't offer alternative-swap chips (no alternatives are persisted) — only "Replace via search", grams edit, delete, and add are available there, unlike the pre-save review screen.
- `updateMealEntryWithItems` (`meal-entries.ts`) replaces an entry's items wholesale (delete all, reinsert) rather than diffing — simplest correct approach given the edit UI always submits the full current item list. It recomputes entry totals from the new items and calls `recalculateDailySummary` for the entry's (unchanged) local day; it never touches `logged_at`.
- `deleteEntryAction` and `updateEntryAction` return a `{ success, error? }` result rather than calling `redirect()` server-side — deliberate, since Next's redirect-from-a-Server-Action-awaited-by-a-client-component relies on an undocumented `error.digest` shape (`next/dist/client/components/redirect-error.js`, not part of the public API) to detect if a caught error was actually a redirect. Returning a result and letting the client call `router.push()` on success (same pattern as Phase 6's `saveMealAction`) sidesteps that entirely. Follow this pattern for any new mutating action called from a client component, rather than reaching for `redirect()` + try/catch.
- Date navigation (`/dashboard?date=YYYY-MM-DD`) is clamped server-side to never exceed "today" in the user's timezone, even if the query param is hand-edited — the "Next" link/button being disabled in the UI is a courtesy, not the actual guard.

## Analytics, charts & streaks (Phase 8)

- `src/lib/streak.ts` is the ONE place the streak algorithm lives: `computeCurrentStreak(loggedDates, todayLocal)` anchors at yesterday (not today) whenever today has no entry yet, so the count never appears to break just because the day isn't over — it only walks backward from today itself once today is actually logged. `computeBestStreak(loggedDates)` is unrelated to "today" — it's the longest run anywhere in history. Both are pure functions over a `Set<string>` of local `YYYY-MM-DD` dates; callers own timezone resolution (via `instantToLocalDate`/`localDayRangeUtc`), these functions never touch a clock.
- `daily_summaries.streak_count` is persisted incrementally inside `recalculateDailySummary` (`daily-summaries.ts`), not recomputed by scanning history: a day with ≥1 entry gets `previousDay`'s persisted `streak_count + 1`; a day with none gets `0`. This makes `streak_count > 0` double as the authoritative "this day had an entry" signal everywhere else in the app — don't use `consumed_calories > 0` for that (a legitimately logged 0-calorie item, e.g. water, would look like a gap) and don't scan `meal_entries` for it (the efficiency requirement in FR-09).
- **This increment only self-corrects forward.** If a much older day's entries are edited/deleted after later days were already recalculated, only that one day's own `streak_count` updates — it does not cascade forward to fix subsequent days' already-stored values. `getStreakHistory` + `src/lib/streak.ts`'s pure functions are what make the _displayed_ current/best streak correct regardless: `/insights` re-derives both from the set of dates with `streak_count > 0`, rather than trusting any single row's stored `streak_count` value directly. Keep reading it that way if you touch this — don't shortcut to `SELECT streak_count FROM daily_summaries WHERE summary_date = today`.
- A `daily_summaries` row is not proof a day was ever "touched" in the sense charts care about — a day whose only entry was later deleted keeps its row (targetCalories snapshot and all) with `consumed_calories` and `streak_count` reset to `0`, per the Phase 7 stale-row gotcha above. `src/lib/insights.ts`'s `SummaryRow.streakCount` is what `buildChartWindow` checks for `hasEntry`, precisely so this case reads as a gap in the chart/stats even though a row exists.
- `src/lib/insights.ts`'s `buildChartWindow(summaries, fromDate, toDate, currentTarget)` is the ONE place gap-filling lives: it walks every calendar day in `[fromDate, toDate]` and fills any day with no row as `{consumed: 0, hasEntry: false}`, keeping the x-axis continuous. Target resolution has two distinct fallbacks that look similar but aren't: a day **with** a row always uses that row's own immutable `target_calories`, even if `streak_count` is `0` (its target was still snapshotted whenever it was first written); a day with **no row at all** (truly never touched) falls back to the user's current profile target, since there is nothing historical to preserve. Don't collapse these into one "hasEntry ? row.target : current" check — they're keyed on different conditions (`row` truthiness vs. `hasEntry`).
- `computeWindowStats` averages intake only over days with an entry (gap days are excluded, not counted as zero — otherwise a sparse window understates real intake) and counts "days on target" using each day's own `target`, not the current one.
- `/insights` (`src/app/(app)/insights/`) fetches one 30-day `getDailySummaries` window and derives the 7-day view by filtering it client-side-of-the-server-component (array slice by date, no second query) — "one query per window" from the FR-09 checklist is satisfied by the existing `(user_id, summary_date)` unique index already added in Phase 1; no new index was needed. `getStreakHistory` is a second lean query (`summary_date` where `streak_count > 0`), also served by that same index.
- `InsightsCharts.tsx` (client component, Recharts `ComposedChart`) renders `consumed` as bars and `target` as a dashed line rather than a single flat `ReferenceLine` — a fixed reference line can't represent a target that changes across history, and per the immutability rule above it does change (a mid-history profile edit only affects days recalculated after the edit). `isAnimationActive={false}` on both the `Bar` and `Line` is deliberate: the default grow-in animation renders a visibly wrong (tiny) chart for its first ~1s, which is confusing on a page whose whole point is "read this number now." The `YAxis` uses a `k`-suffix formatter (`2.2k` not `2200`) specifically so labels stay fully visible at 360px — a bare 4-digit axis label was getting clipped by the negative-margin layout needed to keep the chart within a 360px container.
- Tone is intentionally neutral everywhere on this page (FR-09's "never shame a broken streak"): there's no conditional styling or copy for "streak was broken" — a streak of `0` reads as "no active streak yet... every day is a fresh start," the same structural pattern as Phase 7's non-punitive dashboard rule. Don't add a warning color or icon for a reset streak.
- Manually deleting a `meal_entries` row via raw SQL (rather than the `deleteMealEntry`/`deleteEntryAction` path) leaves a stale `daily_summaries` row behind — this bit us once during manual testing (dashboard showed a nonzero total with an empty timeline). Always delete test data through the app's own functions, or manually delete the corresponding `daily_summaries` row too.

## Export pipeline (Phase 9)

- `export_jobs` is a table not in the FRD §5 DDL — added because FR-10 needs async generation for large ranges, which needs somewhere to persist job state. Columns: `format` (`csv`/`pdf`), `from_date`/`to_date`, `status` (`pending`/`processing`/`ready`/`failed`), `storage_key`, `error_message`, `completed_at`.
- **`src/lib/export.ts` is pure** (no DB, no timezone conversion) — `ExportSourceEntry.localDate` is a plain string the caller must resolve via `instantToLocalDate` before calling in, same pattern as `src/lib/streak.ts`/`insights.ts` taking already-resolved local dates rather than importing `server/lib/timezone` themselves. `src/server/repositories/export.ts`'s `getExportData()` is what actually does that conversion, plus the entries/items/summaries queries, scoped to one `userId` passed in by the caller — it does no authorization itself, so every call site must derive that `userId` from the session, never from a request param.
- `buildExportRows()` (CSV, one row per item) and `buildExportDayGroups()` (PDF, entries grouped by local day) both resolve a day's target/consumed from that day's own `daily_summaries` row when one exists, falling back to a caller-supplied target only when there's no row at all — same immutable-snapshot rule as Phase 8's charts, verified live during manual testing: a stale post-delete row from earlier Phase 8 testing correctly kept its old target in the export instead of picking up a later profile change.
- **CSV is RFC 4180 compliant on purpose, not by accident**: `csvEscapeField` in `export.ts` quotes any field containing a comma, double quote, or line break (doubling embedded quotes); `csvRowLine` always uses CRLF, never bare `\n`; the UTF-8 BOM (`﻿`, written via the explicit escape — never paste the literal BOM character into a source file, since it becomes an invisible, easy-to-mangle byte) is prepended so Excel autodetects the encoding instead of mojibake-ing accented characters. All three were verified against a real download (`xxd`/`od -c`) during manual testing, not just unit tests.
- **PDF generation via pdfkit had two real, easy-to-reintroduce bugs found only by rendering the actual output (poppler's `pdftoppm`/`pdfinfo`), not by unit tests or code review** — both now covered by regression tests in `pdf.test.ts` using `pdf-parse` (`@vitest-environment node` is required in that file; pdfjs-dist silently returns near-empty text under the project's default jsdom environment):
  1. `doc.text(str, x, y, {width})` (used for table cells) leaves `doc.x` pinned at that column's x afterward. Any later `doc.text(str)` call with no explicit position (the day-header/entry-summary lines) inherits that x and gets squeezed into a ~40pt-wide column, wrapping into one word per line. Fix: `resetCursorToMargin()` before every full-width text block, not just after tables.
  2. Writing a "Page X of Y" footer into the bottom-margin zone makes pdfkit think the content overflowed and silently `addPage()`s a blank extra page **per footer call** — so a 3-page document became 6 physical pages while the footer text itself still (wrongly) said "of 3", since `range.count` was computed before that loop ran. Fix: zero `doc.page.margins.bottom` for just that one `text()` call. `file`/`mdls`-style page-count tools can disagree with the footer's own claim when this regresses — that mismatch is the tell.
  - `formatTime()` takes an explicit `timezone` parameter and must never default to UTC or server-local time — this is the same class of bug the whole project's timezone rule exists to prevent, just inside a PDF instead of the dashboard. Regression-tested in `pdf.test.ts`.
- **Sync vs. async is decided by `daysBetweenInclusive(fromDate, toDate) > ASYNC_JOB_THRESHOLD_DAYS` (90)**, in `src/server/export/range.ts`, checked identically by both `/api/export/csv` and `/api/export/pdf`. Under the threshold, the route generates and returns the file directly in the same request (CSV via a genuinely chunked `ReadableStream`; PDF as one buffer, since pdfkit's own output is small enough at that range that buffering isn't worth streaming). Over the threshold, the route creates an `export_jobs` row and returns a 302 redirect to `/export?pending={jobId}` **without awaiting generation** — `runExportJob()` runs detached (`void runExportJob(...)`). This project has no external job queue (no Redis/SQS); a detached async function is the deliberate stand-in given the app's scale, and only works because it's a long-lived Node process (`next start`/`dev`), not a serverless function that could be frozen once the response is sent. Don't "fix" this by awaiting it — that would defeat the entire point of the async path.
- **The download link is a presigned GET straight to the bucket, not a proxy through our server**: `createPresignedExportDownloadUrl()` sets S3's `ResponseContentDisposition`/`ResponseContentType` params so the correct filename/content-type arrive without our Node process ever touching the file's bytes on the way out.
- **Every export route/job function that takes a `jobId` must go through `getOwnedExportJob(jobId, userId)`** (`export-jobs.ts`) — it scopes the lookup to `(jobId, userId)` in one query rather than fetching by `jobId` alone and checking `.userId` afterward in application code, so a missed check can't silently leak another user's job; a mismatched pair simply returns nothing, identical to a nonexistent job. Never add a route that calls a bare `getExportJob(jobId)` — there isn't one, on purpose. Proven both at the repository level (`export-jobs.test.ts`, two real users in Postgres) and end-to-end (`e2e/export.spec.ts`'s second test, two separate authenticated Playwright browser contexts: the attacker gets a 404 from both the status and download routes for the owner's real job).
- The `/export` page itself needs **no client JS to trigger a download**: both buttons are `type="submit"` inside one `<form method="get">` with per-button `formAction`, so a plain browser navigation (not a `fetch`+Blob+`a[download]` dance) hits the route and the browser downloads natively off `Content-Disposition: attachment` — this is what makes the sync path "just work" identically on desktop and mobile Safari/Chrome without any download-specific JS to get wrong. The async path's only JS is `ExportJobStatus.tsx` polling `/api/export/jobs/{jobId}` every 2s — the actual download, once ready, is again a plain `<a href>` to the download route, same reasoning.
- **Known gap, not fixed in this phase**: deleting a `users` row cascades `meal_entries`/`meal_items`/`daily_summaries`/`export_jobs` in Postgres, but does **not** delete that user's objects (meal photos, generated exports) from S3/MinIO — S3 isn't part of the transaction. Hit this during e2e test cleanup (orphaned `users/{id}/exports/*.csv` objects after deleting the test user). No user-facing "delete my account" feature exists yet for this to matter to a real user; worth remembering if one is ever added.

## NFR hardening & release metrics (Phase 10)

- **`src/middleware.ts`'s `secureCookie` check must key off the request's actual protocol, never `NODE_ENV`** — found as a real, previously-latent bug while building this phase's own 4G-latency test harness (`e2e/perf-4g.spec.ts`), which runs a genuine production build (`next start`) locally over plain HTTP. `getToken({ secureCookie: process.env.NODE_ENV === "production" })` looked for the `__Secure-`-prefixed cookie name whenever `NODE_ENV=production`, but Auth.js core's own default (`@auth/core`'s `init.js`: `config.useSecureCookies ?? url.protocol === "https:"`) — which `src/auth.ts` doesn't override — only sets that prefix when the _request_ is actually HTTPS. Serving a production build over plain HTTP (this local harness, or a real deployment with TLS terminated upstream without forwarded-proto handling) meant login always "worked" but every subsequent protected-page request looked signed-out. Fixed to `secureCookie: req.nextUrl.protocol === "https:"`, matching Auth.js's own logic exactly. If you ever touch this line, re-verify by actually running `npm run test:perf` (or any `next start` flow) over HTTP, not just `next dev`.
- **The perf/Lighthouse numbers in this project's history are only meaningful against a production build, not `next dev`** — dev mode lazily compiles each route on first request (which can itself take several seconds) and ships unminified bundles, so `e2e/perf-4g.spec.ts` has its own `playwright.perf.config.ts` (`npm run test:perf`) that runs `next build && next start` and is excluded from the main Playwright config (`testIgnore`) rather than sharing the dev-server-based `webServer`. Don't fold it back into the main config.
- **CSP is nonce-based, generated per-request in `src/middleware.ts`** (Next's own documented recipe), not a static header in `next.config.ts` — the other security headers (`X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, HSTS) _are_ static and live in `next.config.ts`'s `headers()`, since they don't need a per-request value. `script-src` needs `'unsafe-eval'` in development only (Next dev's HMR runs itself through `eval()`) — never drop the `NODE_ENV` branch there or `next dev` breaks with CSP violations. The middleware's matcher was widened from "protected routes only" to "every route except static assets" specifically so these headers apply site-wide, not just to authenticated pages — the auth-redirect logic inside the function is unaffected, it still only fires for `PROTECTED_PREFIXES`.
- **Rate limiting is Postgres-backed (`rate_limit_counters`, fixed-window), not in-memory or Redis** — this stack has no Redis, and a real production deployment could run multiple instances, so an in-memory counter would silently under-count. `src/server/lib/rate-limit.ts`'s `checkRateLimit(key, limit, windowSeconds)` is the only place this logic lives. The signup limit (`src/app/signup/actions.ts`) is deliberately generous (200/IP/hour, raised from an initial 30 after hitting it firsthand during this phase's own testing) — every local request (dev server, e2e suite, manual testing) collapses onto one shared loopback-IP bucket, so it needs headroom for many e2e runs across a day of iteration, not just one run. Login is rate-limited by email instead of IP (10/hour) since that's what actually stops one account from being brute-forced; a rate-limited login and a wrong password both just return `null` from `authorize()` — never a distinct signal that would tell an attacker they'd hit a limit rather than guessed wrong.
- **`/admin/metrics` has no role column to check** — `users` was never given one (adding it is more schema churn than an internal metrics page justifies), so it's gated by an `ADMIN_EMAILS` env-var allowlist checked against `getEffectiveUser()`, same auth convention as every other protected page. Unauthorized (including logged-out) visitors get `notFound()`, not a login redirect — deliberately doesn't confirm the route exists to someone probing it.
- **`getMealEditRate()` (FR-10 release metric) and `getStreakDistribution()` are both genuinely global, unscoped aggregates** — don't write a test that assumes exact before/after deltas against them; the shared dev Postgres has other test files and e2e runs writing to `meal_entries`/`daily_summaries` concurrently. `metrics.test.ts` uses `toBeGreaterThanOrEqual` bounds for exactly this reason, not because the underlying logic is fuzzy.
- **`@sentry/nextjs` and its three config files (`sentry.server.config.ts`, `sentry.edge.config.ts`, `src/instrumentation-client.ts`) are all genuinely no-ops without a DSN** — `Sentry.init({ dsn: undefined })` is safe and does nothing, so none of this requires a Sentry account to be correct. The one thing that isn't optional: `beforeSend` strips the `key` query param from any captured request URL in both the server and client configs, since that's exactly the storage-key-leak the phase's privacy pass rules out — don't add a new query param elsewhere without checking whether it needs the same scrub.
- **Two Server Action leak vectors were found and fixed during the leak audit, not by inspection alone**: `saveMealAction`, `updateEntryAction`, and `deleteEntryAction` used to return `err.message` straight to the client on failure — repository errors like `User {id} not found` or `Meal entry {id} not found` (`meal-entries.ts`) would have leaked internal ids into a user-visible error string. Fixed to log the real error server-side (`logEvent`) and return a fixed generic message instead. Same fix applied to the export job runner's stored `errorMessage`, since `/api/export/jobs/{jobId}` echoes that field straight back to the client. **Any new Server Action catch block must follow this pattern — never `err instanceof Error ? err.message : fallback` for a user-facing error.**
- **The Lighthouse mobile scores (dashboard/insights/login all ≥93 performance, 100 accessibility after fixes) surfaced two real, fixable a11y bugs, not just abstract audit noise**: the disabled "Next →" pagination control was `text-[var(--foreground)]/30` on a near-black background (2.37:1 contrast, needs 4.5:1) — bumped to `/50`; and every header nav link/Sign out button was a bare inline text link with no padding, under the 24×24px minimum touch-target size — fixed with `py-1.5` + a compensating `-my-1.5` (grows the tap target without changing the header's visible height or spacing). Re-verify with real Lighthouse (`npx lighthouse <url> --form-factor=mobile --screenEmulation.mobile`) against a running production build if you touch header/nav or any low-opacity text class — don't trust "it looks fine" for either contrast or tap-target size.
- **The accuracy harness (`scripts/run-accuracy-harness.ts`, FR-05's top-3 identification metric) is real, tested infrastructure — but running it against the mock provider is not a real accuracy measurement**, since the mock always returns the same fixed 3 items regardless of the input photo. `fixtures/accuracy/cases.json` deliberately includes one case with correct labels and one with deliberately wrong labels specifically so a run proves the scoring logic discriminates hits from misses (currently reports 60% against mock, by design) rather than vacuously reporting 100%. Don't cite that number as a real accuracy result in any report — it isn't one until real labeled photos + `VISION_PROVIDER=anthropic` are used.
